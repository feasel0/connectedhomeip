## Findings

### R1: Unsupported Command Bounds Abort IDM Instead Of Reporting A Coverage Gap

Priority: P1 for devices exposing affected commands.

`src/python_testing/support_modules/idm_support.py:1448` calls
`Constraints.require_supported()` during command resolution. The command loop
at `src/python_testing/TC_IDM_9_1.py:104` catches only `ChipStackError`, not
`SpecParsingException`. Thus a harness limitation can terminate the entire test
before the device receives a request or its behavior is assessed.

Using the exact published parser and IDM source, the current model/generated
command descriptors contain 15 unresolved command-field expressions outside the
new recognizers. Direct helper calls reproduced the exception for Camera AV
Stream Management VideoStreamAllocate MinFrameRate/MinBitRate and Electrical
Alarm SetElectricalAlarmThresholds OverVoltageThreshold. Both commands are
outside the existing exclusion lists. No controller or device I/O was performed.
This is not proof all 15 fields are selected on every device; applicability and
exposed command lists still control discovery.

The attribute loop behaves differently: it catches exceptions and skips the
probe. Three current writable attributes carry unsupported expressions: Audio
Control DefaultStepSize and StartUpVolume, and Boolean State Configuration
CurrentSensitivityLevel. This is a real coverage limit, not an observed whole-test
abort on the attribute side.

Recommendation: distinguish unsupported harness evaluation from invalid DUT
behavior with explicit path-level coverage reporting and an intentional overall
coverage policy. Do not silently discard expressions or add a broad exception
catch that hides genuine defects. Complete the evaluator for required current
paths rather than treating a fail-closed exception as conformance coverage.

### R2: New Regression Files Are Not Registered In CI

Priority: P2.

`.github/workflows/tests.yaml:1218` invokes the existing test_idm_support module
explicitly. It does not invoke the new test_idm_unsupported_constraints module,
and the nearby unittest discovery is limited to mDNS tests. Searches of workflows,
test runners and ZAP scripts found no invocation of the new negative-constraint
suite or the new test_cluster_constraints script. Their local passes therefore
do not establish continuing PR CI protection.

Recommendation: move cases into already executed suites where practical, or add
explicit calls to the owning existing CI steps. No new test framework is needed.

### R3: Absolute Local Roots Were Introduced In Published Provenance Comments

Priority: P2 publication/reproducibility issue, not a protocol behavior defect.

The four targeted generated ZAP files contain absolute sdk-root/spec-root
arguments at line 20. Their PR-base headers did not contain those absolute root
arguments. The affected files are Closure Dimension, EPA, global enums and global
structs. These are XML provenance comments, not generated C++ API headers.

The root writer is Alchemy's zap/render/version.go:114: patchAlchemyComment
copies os.Args[1:] and removes only the leading double dash and .adoc arguments.
It consequently records machine-specific root paths. That file is unchanged
between the Alchemy upstream base and our combined access/bitmap patches. The
SDK reference-generation wrapper is not the component writing this comment.

Assessment: existing Alchemy behavior is the root cause, but the newly published
artifacts are our PR's responsibility. Neither external Git-service errors nor
the pre-existing nature of the writer excuses the new artifact defect.
Recommendation: normalize root arguments in Alchemy or use a portable canonical
invocation, then regenerate the affected outputs with truthful provenance. Do
not fake metadata or broadly rewrite generated semantic content by hand.

### R4: Humidistat Zero Policy Remains Inconsistent

Priority: P2 incomplete domain-policy resolution.

HumidistatCluster.cpp:778 rejects zero in WriteAttribute. The public setter at
line 503, SetSettings at line 849 and startup/persistence paths can still produce
or retain zero. New tests explicitly expect direct setter/command zero success.
The attribute guard itself is a small correct implementation of that attribute
bound; it does not establish a consistent stored-state invariant.

The new error log at line 236 states that specification clarification is needed
while startup continues unchanged. That is development-process commentary in
shipping firmware, not useful remediation for a device operator. Remove it or
replace it with a concrete diagnostic only when the resolved policy warrants it.
Do not independently move the guard into SetMistType until optional-command and
legacy-storage semantics are decided; that would silently choose a broader policy.

### R5: Historical Diagnostic Matching Does Not Prove Notice Identity

Priority: P2 regression-test quality.

TestSpecParsingSupport.py:281 adds a substantial source matcher plus expected
category totals for ten model versions. A negative control on the real 1.4 model
kept all 40 notices but replaced one derived-attribute notice with a duplicate
from a different attribute path. The validator still passed. Total/category and
source membership checks therefore do not prove every original notice survives.

Recommendation: use a multiset of stable identities including location, severity
and message where practical, with a negative control for one missing/repeated
notice. Separate this larger diagnostic-baseline work from the small caller-list
propagation fix when reducing integration review scope. Do not hide historical
warnings or restore the original lost-list behavior.

## Simplicity Assessment

| Area | Assessment |
| --- | --- |
| Closure Dimension | Bounds/divisibility checks and constructor enforcement are conservative. Public ValidatePositioning is an extra API, but allows recoverable preflight and follows existing configuration-validation intent; not a required redesign. |
| EPA | Explicit feature/null/optional-aware minima checks are straightforward. ValidateRatingMinima is additive API, not a full validator. Retain unless no application preflight use is intended. |
| Humidistat | One-line attribute guard is minimal. Startup policy log and partial zero-state policy are not a finished uncontroversial resolution. |
| ModeBase | More justified than initially apparent: ModeBase::Commands aliases ThermostatMode::Commands, so updating Thermostat metadata would otherwise change all derived modes' access. Current explicit Operate entries prevent that. They assume empty command-quality flags; prefer per-cluster generated metadata or a small documented stable shared entry if simplifying. |
| Thermostat metadata | This PR alone still has generated Operate metadata. Manage enforcement depends on separate #74803. Keep the dependency visible and validate the combined state before claiming the ACL change complete. |
| Wi-Fi scan | Four-line sentinel-to-wire-bit translation plus a private decoder overload for real GDBus cached-property tests is a reasonable narrow change. Older advertised-version interpretation remains unresolved; TLV round-trip tests do not prove that policy. |
| Parser inheritance | Missing-versus-explicit conformance flag and base overlay merge are warranted. Caller-list extension and direct integer parsing are small root fixes. |
| Constraint evaluator | Not the simplest or least controversial part: roughly 200 added IDM lines include repeated XML recognition, cluster/class/name/ID checks and DEM-specific payload construction inside a generic helper. Prefer one parsed expression representation/evaluator and a narrowly isolated companion-value policy; avoid expanding into a general interpreter without demonstrated consumers. |
| GKM/DEM/Push/native tests | Mostly targeted coverage rather than production changes. Real IM/TLV and native validation paths justify some fixture size; preserve named request descriptors and normal-target registration. |
| Diagnostic tests | Much broader than the loader fix, coupled across test classes and versions, and missing identity controls; strongest candidate for a separate or simplified test-maintenance change. |

Overall: no, not every SDK change is the smallest and least controversial form.
The simple validators, loader/inheritance fixes and scan translation can remain.
Prioritize actual command abort/coverage behavior, CI registration and consistent
domain policy before cosmetic reductions. Do not split or duplicate the existing
integration PR as part of this review.

## Verification And Limits

- Live PR title/head/draft confirmed; SDK diffs read from committed HEAD, not
  uncommitted local test edits.
- Four published provenance blocks compared with the base; Alchemy writer diff
  checked against its upstream base and found unchanged.
- Imported parser and IDM source hashes matched the committed PR blobs before
  behavior probes. Existing host native modules and model package were reused.
- Attribute and command probes executed without hardware/network side effects.
  First exploratory commands required corrections for generated-class registry
  imports and commandless clusters; only the corrected successful results above
  are evidence.
- Diagnostic positive control passed before the missing/repeated-notice negative
  control unexpectedly passed. This is a test weakness, not a new production fix.
- No broad native rebuild, full certification run or fresh full generation was
  performed for this review. Prior passing counts are not a substitute for these
  newly identified gaps.
- Recommendations remain unapplied pending the user's decision. Only internal
  reporting changes are committed to the dedicated fork-only data-model branch.
