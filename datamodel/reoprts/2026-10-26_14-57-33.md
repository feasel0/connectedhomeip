## 4. Necessary And Minimal Correction

Current production requires MotionZones presence only inside its Motion branch, while the Ambient branch only prohibits MotionTimeControl. The allocation-level zone-list guard is likewise Motion-only. Consequently, the omission and malformed Ambient cases return a success response and allocate a connection in fresh 516d execution; the same faulty code remains at f93e. This is a behavioral defect, not merely missing test coverage.

The correction shares only the presence guard across Motion/Ambient, then leaves the existing Motion timing/sensitivity block separate. A second predicate includes Ambient in the existing allocation checks. Existing statuses, duplicate/null semantics and delegates are reused. Null/empty acceptance, Continuous/Command rejection, Motion-only timing and sensitivity behavior are preserved. No new list minimum, feature policy, status mapping, revision bump, data-model regeneration or API was invented.

The shared validator also serves ModifyPushTransport, so omitted mandatory Ambient MotionZones will correctly reject there as well. The candidate is not a complete audit or refactor of Modify/UpdateMotionZoneOptions. Broader populated Ambient per-entry sensitivity, malformed nested decoding, ZoneUse and no-ZoneManagement delegate behavior are not claimed repaired by these two guards. Their preexisting implementation and full conformance need separately scoped review; they are not a reason to keep accepting the concrete missing/duplicate/oversized/invalid-ID cases established here.

Compatibility impact is intentional: previously accepted Ambient omissions and malformed lists now fail with normative statuses. Valid explicit null/empty/populated cases keep working. This is safe as a bounded merged-1.7 correctness correction, not a blanket promise for older releases, all device feature selections or all camera implementations.
