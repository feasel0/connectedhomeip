## 2. Normative Requirements

The SDK's Matter 1.7 model pins specification **eea0ffce8fe9e4951a4558a6e6c6362b307e0334**. Authenticated GitHub contents/tree access retrieved the exact private chapters; current specification master **bbd2ce19b81b1973b2e537eec989f841ef02fcb6** was also inspected for the Closure Dimension requirements. The current chapter expresses the minimum as 0.01% and removes the older fallback cells/prose; the numeric minimum and divisibility rule agree. Default1 below refers to the pinned model/SDK, not a current-spec normalization mandate. No private specification source is republished.

| Requirement | Authoritative Source | Consequence |
|---|---|---|
| percent100ths has semantic range 0..10000 | Data-Model.adoc, Percentage100ths Type, line 3181 at pinned SHA | C++ uint16 storage does not make 10001..65535 valid attribute values. |
| Resolution and StepValue each have minimum 1 and fixed quality | ClosureDimension.adoc attribute table, lines 430-431 | Each is 1..10000 when Positioning is supported; zero is forbidden. |
| StepValue is an integer multiple of Resolution | StepValue section, line 500 | StepValue % Resolution must equal zero, after first proving Resolution nonzero. Positive bounds also imply StepValue >= Resolution. |
| Both attributes have PS conformance | Same attribute table | Positioning-off configurations do not expose these attributes; unused fields must not create new restrictions. |
| TargetState.Position is an integer multiple of Resolution | TargetState section, line 476 | Application target updates must satisfy the scaling rule. |
| LimitRange endpoints are multiples of Resolution | LimitRange section, line 567 | These are range/command-state requirements, not additional configuration-number bounds. |
| SetTarget selects a nearest valid position; Step applies a delta and clamps | SetTarget/Step sections, lines 648 and 792-794 | Command processing must remain consistent with legal position bounds and target scaling. |

The reference XML at data_model/1.7/clusters/ClosureDimension.xml uses percent100ths plus min 1, fixed persistence and PS conformance. ZAP's closure-dimension-cluster.xml explicitly has min 1/max 10000/default 1 and PS conformance for both attributes. Neither scalar XML declaration enforces the cross-field multiple relationship. TC_CLDIM_2_1.py lines 179-197 checks the same numeric bounds and divisibility; its assertions corroborate the specification, rather than create the rule.

**There is no established requirement that Resolution divide 10000.** For example, (3,3), (3,9999), (9999,9999) and (6000,6000) meet the configuration rules. Rejecting those solely to avoid command edge cases would invent a new restriction. Fallback/default 1 is not a license to silently replace explicit invalid application input. CHIP_ERROR_INVALID_ARGUMENT is the candidate's application-API error, not a specification-mandated C++ constructor status.

## 3. Current Construction And Publication

Config::WithPositioning sets the feature and copies both uint16-backed values without validation. Public Config members allow bypassing the builder as well. The constructor copies both values and checks feature combinations with existing fatal checks, but does not check either bound or their relationship. DefaultServerCluster::Startup accepts them. Attributes advertises both entries for PS, and ReadAttribute encodes the stored values unchanged.

The integration's first Interface::Init overload stores conformance/parameters; its second builds Config, constructs mCluster and registers it without validating these numbers. The direct all-devices ClosurePanel path also accepts them, constructs the cluster, initializes current state and calls AddCluster. Existing Linux/Silabs closure-app values are valid (100,1000); defaults are (1,1). ClosureDimensionEndpoint propagates integration Init errors. The example managers choose their existing application-level VerifyOrDie policy; the candidate does not add another fatal cluster invariant.

An important SDK convention prevents a startup-only fix: ServerClusterInterfaceRegistry::Register logs a failing Startup but still returns success/inserts the entry. Register-before-context similarly leaves the entry present when SetContext reports CHIP_ERROR_HAD_FAILURES. Both orderings were executed. Therefore rejecting Startup alone cannot prove invalid attributes/commands are inaccessible. Returning an empty GetPaths is also inappropriate: the interface contract requires a nonempty stable path set.

The prior CDIM-01 ledger's closed disposition described an earlier broad/local proposal, not current-master enforcement. This investigation reopens it based on fresh executed upstream evidence; historical reports remain unchanged.

## 6. Local Candidate And Compatibility

The candidate changes exactly four existing cluster-owned files, **+192/-4**: ClosureDimensionCluster.h/cpp, CodegenIntegration.cpp and the existing TestClosureDimensionCluster.cpp. No generated model/artifact, unrelated cluster, example source or Python test is modified.

- Add recoverable Config::ValidatePositioning: PS-only bounds first, then divisibility. Preserve caller values; do not normalize or require a divisor of10000.
- Call it before integration mCluster.Create, returning InvalidArgument through the existing CHIP_ERROR Init API.
- Cache one immutable validity boolean in the direct cluster, return InvalidArgument at Startup, and reject reads/commands/application mutations for an invalid object. This closes the actual registry-retention behavior without changing the shared registry or adding path-existence checks.
- Preserve existing constructor/WithPositioning signatures, all valid values, feature combinations, getters and valid command behavior. No new fatal assertion, allocation, new file target or revision bump.

The extra guards are not redundant path validation: they handle an invalid immutable application configuration that can remain registered after failed startup. A Config-only validator would be opt-in and bypassable; constructor-only recovery has no error channel; startup-only rejection is insufficient under actual registry semantics. Integration preflight plus fail-closed direct instances is the smallest implemented alternative that covers both callers without a factory migration or shared-registry behavior change.

Source compatibility is retained for existing valid callers, including application setters used before Startup. The new validation method is additive. Object layout changes by adding a boolean member, so binary consumers must rebuild; no particular sizeof increase is claimed. Direct getters still report the originally supplied values for diagnosis; invalid objects can still exist and be registered, but cannot encode values or execute mutations/commands. Generic Register success is not newly promised to propagate Startup failures. A factory/registry-wide admission redesign would be a separate API decision, not hidden in this correction.

## 7. Valid-Input Command Findings And Owner Questions

Two additional probes use configurations valid under the established rules, no Limitation feature, and a valid current position0. Both reproduce identically on pristine upstream and candidate:

1. Resolution6000/StepValue6000, SetTarget position10000: nearest rounding computes12000, the delegate is called, then SetTargetState rejects the out-of-range target. The command fails after a side effect instead of selecting a valid reachable endpoint/grid point.
2. Resolution3/StepValue3, Step increase65535: delta exceeds the upper endpoint, so clamping yields10000; the delegate is called, then SetTargetState rejects10000 because it is not divisible by3. The command fails after a side effect.

These are not candidate regressions, configuration violations or sanitizer findings. They show why valid Resolution must not be restricted to divisors of10000 merely to make existing code pass. No unrelated command fix was silently added. The exact nearest-valid-point/endpoint interpretation must reconcile the target scaling rule with Step's explicit upper clamp. Owners should decide the bounded rounding/clamp policy and delegate-before-validation ordering, then add reproducing command regressions before a further correction.

Owners should also confirm the preferred direct-instance invalid-configuration policy: inert object plus recoverable errors versus a future fallible factory/registration contract. The existing constructor's other fatal feature checks and stale README examples were inspected but intentionally not refactored. The integration translation unit is compiled/analyzed under mock ZAP headers; a complete real application Init/registration test remains a qualification limitation, not an exercised singleton path.
