## 2. Four-File Safety Audit

- `Config::ValidatePositioning()` is PS-conditional: both numeric values must be 1..10000, then StepValue must be divisible by Resolution. The zero/range checks precede modulo. It neither normalizes explicit input nor rejects legal non-divisors such as 3, 9999 or 6000.
- The constructor preserves supplied numbers and caches validity. Its feature/numeric fields are copied and not subsequently mutable through an API, so the cached result cannot become stale through normal use.
- `Startup()` rejects invalid positioning before initializing the base context. `ReadAttribute`, `InvokeCommand`, and the four state/range setters independently reject invalid retained instances before arithmetic, readback, mutation or delegate invocation.
- Codegen `Init()` validates before lazy construction and before registry publication. Its earlier parameter-storing overload still succeeds; the parameterless initialization step supplies the recoverable rejection.
- The four new methods remain in the existing native test file. No generated source, shared registry, application, build configuration or command rounding/clamping code changed. Constructor initializer formatting is the only nonbehavioral production churn; no broader cleanup is necessary.

The bounded Step product is at most 65535 * 10000 = 655350000, within signed 32-bit range. Rejecting invalid StepValue before arithmetic therefore closes the reproduced integer-promotion overflow without changing legal command arithmetic. Zero Resolution is rejected before each reproduced modulo/division path.

## 3. Invalid Instances, Registry Orders and Compatibility

The actual shared registry intentionally retains failed-startup entries. With context already set, `Register()` logs the Startup failure, inserts the entry and returns success. With registration first, `SetContext()` returns aggregate `CHIP_ERROR_HAD_FAILURES` but retains the entry. Both paths later pair Shutdown with failed Startup. The candidate does not change these semantics or falsely claim registration failure propagation.

Consequently, bridge preflight prevents ordinary codegen publication, while instance guards quarantine invalid objects registered directly. Metadata/path discovery is unchanged; paths remain stable and nonempty. An invalid direct instance can still be located and described, but cannot encode invalid attribute values or execute its guarded operations. Returning empty paths or relying on Startup alone would not satisfy this contract. The retained native registry tests exercise both actual orderings, rather than a registry mock.

With PS off, unused zero/above-range numeric fields are not rejected. Positioning attributes remain absent, positioning/range APIs retain their unsupported-feature behavior, and latching remains functional. Direct diagnostic getters preserve the original invalid numeric values. In contrast, the bridge has no constructed instance after preflight rejection, so its ordinary getters return incorrect-state rather than exposing a fabricated cluster.

Existing public constructors/builders/getter signatures are preserved; the validator and Startup override are additive. The new private const bool changes the class definition/layout: binary consumers must rebuild. No sizeof increase was measured and no stable binary-layout guarantee is claimed. Rejecting previously accepted invalid input is intentional. Existing feature-combination fatal checks and Shutdown's constructed-instance precondition are unchanged; callers must honor failed Init and not invoke Shutdown as if initialization succeeded.

The closure example propagates both Init results; its Linux/Silabs configuration uses valid 100/1000 values. The all-devices ClosurePanel path calls SetCurrentState before provider AddCluster, so the new guard statically makes invalid positioning fail before that publication within its existing transaction. That application path was inspected, not built or executed. Full ABI consumers, whole applications, physical motion and hosted CI remain outside the established evidence.

## 5. Case A: Independent SetTarget Defect

Inputs: PS on, LM off, Resolution6000, StepValue6000, current position0, SetTarget position10000, delegate succeeds. These are valid configuration/command values. Both original and safety candidate compute12000, call HandleSetTarget once with the rounded position, then return Failure when SetTargetState rejects the out-of-domain result. The retained sanitized child records contain no arithmetic-UB diagnostic for this case; this is a semantic defect, not the invalid-input UB mechanism.

The bounded legal grid is {0,6000}. Its nearest eligible target to10000 is6000;12000 is outside percent100ths and10000 is not an integer multiple. Reading the domain and nearest-valid rule together supports bounded nearest-multiple selection followed by Success, assuming the usual state/delegate prerequisites. ConstraintError is specified for an out-of-domain supplied position, not merely for a valid position needing quantization; rejecting this10000 request is not the supported repair. No special10000 exemption was found.

For LM on, the eligible set is grid multiples inside the valid aligned LimitRange. Clamping to its endpoints before nearest rounding cannot overshoot that aligned interval. A nominal [0,10000] range is not itself valid for Resolution6000; [0,6000] is. This does not justify restricting the configuration domain.

Exact equal-distance ties are not decided by the inspected SetTarget wording. The current integer formula selects the upper neighbor for representable ties. Either equally nearest eligible neighbor satisfies the distance rule absent additional guidance; changing the established tie choice should be a separate deliberate decision, not an accidental part of the safety correction. Case A is not a tie:6000 is the sole closest eligible point.

Classification: **independent preexisting command defect**, with a sufficiently grounded bounded-grid repair direction. No repair was incorporated here.

## 6. Case B: Separate Step Interpretation Gap

Inputs: PS on, LM off, Resolution3, StepValue3, current position0, Increase65535 steps, delegate succeeds. Both original and candidate calculate delta196605, clamp to10000, call HandleStep once, and return Failure when target scaling rejects10000 modulo3. There is no invalid configuration, signed overflow or sanitizer diagnostic in this case.

Step's explicit upper endpoint/success rule points to10000, while the general TargetState rule excludes that nonmultiple. No exception/precedence clause was found. Choosing9999 preserves grid membership but changes the literal upper clamp; admitting10000 adds an exception not stated in the inspected target rule. Therefore the exact replacement target and success behavior cannot be selected confidently by implementation alone. The current post-delegate Failure is not a specified resolution of that conflict, and no new ConstraintError policy should be invented for otherwise valid inputs.

LM with an aligned maximum9999 removes this particular upper-endpoint conflict. The lower endpoint0 is always a multiple; aligned LM endpoints are also multiples. A separate issue may exist when stepping from an arbitrary off-grid CurrentState, but it was not independently reproduced or broadened into this task.

Classification: **unresolved specification interpretation affecting independent preexisting Step behavior**, not an inseparable configuration-admission problem. Resolution3/StepValue3 remains legal and must not be rejected to hide the conflict.

## 7. Delegate Ordering and Owner Questions

The observed defect common to A/B is action dispatch before the server discovers that its computed target is unacceptable. Calls were counted in native fixtures; actual physical side effects were not tested. A future command-specific change should compute and validate the final target before invoking a potentially side-effecting delegate, then preserve existing delegate-failure semantics and publish state only on accepted action. Merely moving state mutation before the delegate would create a different failure-mode risk.

Questions prepared only; no outreach, assignment or review request:

1. For Step saturating at10000 with a legal non-divisor Resolution, should an explicit endpoint exception apply, or should the effective clamp be the greatest in-range grid point? Which requirement should be clarified, and should the accepted action return Success as the Step rule indicates?
2. Confirm bounded nearest-valid selection for SetTarget, including Case A's6000 result, and whether an exact grid tie needs a prescribed direction rather than preserving existing upper-neighbor behavior.
3. Confirm the intended application delegate contract for validating/resolving the target before action dispatch, while retaining no target publication when the delegate rejects.

These are command-specific owner decisions, not conditions to silently add to `ValidatePositioning()`. The layout/rebuild caveat should be made explicit in any future safety PR.
