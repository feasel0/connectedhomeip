## 4. Callback, State And Queue Mechanism

The mechanism is directly supported by the tested sources, not inferred solely from log proximity:

1. [ReadClient::ProcessReportData](https://github.com/project-chip/connectedhomeip/blob/db3ce1431d8c9bc6dd97142cd2ede5f7e47a0a00/src/app/ReadClient.cpp#L714) calls `OnReportEnd` after the final report chunk, then moves an initial subscription into `AwaitingSubscribeResponse`. Report completion is not subscription establishment.
2. The Darwin report-end block dispatches `_handleReportEnd` asynchronously to the device queue. That method calls the debug delegate hook `unitTestReportEndForDevice:` through the delegate's configured queue; `MTRDeviceTestDelegate` invokes `onReportEnd`, fulfilling the tests' priming expectation.
3. [ReadClient::ProcessSubscribeResponse](https://github.com/project-chip/connectedhomeip/blob/db3ce1431d8c9bc6dd97142cd2ede5f7e47a0a00/src/app/ReadClient.cpp#L1118) handles a separate later protocol message and invokes `OnSubscriptionEstablished`. The Darwin established block synchronously changes the internal state on the Matter queue, then schedules device-queue work.
4. [The enum](https://github.com/project-chip/connectedhomeip/blob/db3ce1431d8c9bc6dd97142cd2ede5f7e47a0a00/src/darwin/Framework/CHIP/MTRDevice_Internal.h#L34) defines 1 as `Subscribing`, explicitly including receipt of priming reports, and 2 as `InitialSubscriptionEstablished`, meaning initial establishment has completed at least once. State 2 does not by itself promise the subscription remains currently healthy forever.
5. `_changeInternalState:` requires the Matter queue and `_lock`; `_getInternalState` takes that same lock. `syncRunOnWorkQueue:` and `unitTestSyncRunOnDeviceQueue:` each use `dispatch_sync` on their respective queues. They order already-enqueued work, but do not wait for a future SubscribeResponse/network event. A priming callback plus these barriers therefore does **not** guarantee state 2. There is a legal scheduling interval in which the test reads 1, exactly as observed.

The second ordering is not proof that state 2 preceded the actual getter: the getter returns a locked snapshot; another thread can establish the subscription before XCTest formats/emits the failed comparison. Log interleaving does not timestamp the getter, expectation fulfilment or individual barriers. The source establishes the missing synchronization; these observations are consistent with it. The original `test048i` passes on attempt 2, while a different test using the same setup fails.
