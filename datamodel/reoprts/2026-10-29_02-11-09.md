## 1. How We Found This Particular Error

Our first recorded encounter with this subscription-test setup failure was normal hosted Darwin CI while qualifying Closure Dimension configuration-safety PR [#75000](https://github.com/project-chip/connectedhomeip/pull/75000): workflow 40649659154, TSAN job 122690768959. Later, bounded-rounding PR [#75019](https://github.com/project-chip/connectedhomeip/pull/75019) failed the same initial-state prerequisite in test048i, then equivalent test048e on its already-completed retry. These were XCTest assertion failures inside a TSAN-enabled job, not demonstrated ThreadSanitizer memory-race findings.

That establishes a preexisting upstream test defect; it does not measure whether unrelated patches influence its scheduling or failure frequency. The [source-matched investigation](2026-10-28_21-55-27.md) preserves the exact checkout identities, logs, checksums and callback evidence.

## 2. Was This an IDM Coverage Mismatch?

**No.** This failure was not discovered by an IDM coverage comparison, missing-field inventory, XML/model mismatch or the independent IDM constraint-parser correction. Existing Objective-C subscription tests failed during ordinary CI. The failing assertion expected an established subscription even though the setup had waited only for the initial report to finish.

The protocol events are distinct: final priming report completion can precede SubscribeResponse and the establishment callback. A synchronous queue drain cannot wait for a future network response. The test can therefore legitimately read Subscribing, state 1, while incorrectly expecting InitialSubscriptionEstablished, state 2. The state access itself is locked; the synchronization condition is wrong.

## 4. Is This the Smallest and Most Obvious Fix?

**It is a strongly supported minimal correction, but universal agreement cannot be guaranteed.** The same test file already provides `_expectationForSubscriptionEstablishedOfDevice:delegate:queue:description:onEstablished:` and a neighboring subscribed-device helper already uses it. Reusing the existing expectation makes setup wait for the condition the unchanged next assertion actually requires.

Exactly three affected setup blocks are replaced, one file +3/-12. Each of test048c, test048e and test048i has an observed failure of this setup across the recorded controls. The callback is installed before starting the subscription; all other file bytes, strict initial-state assertion, 60-second waits, queue drains, pool counters and late resubscription/invalidation/ReadClient assertions remain unchanged. No sleep, timeout increase, state-1 acceptance, new abstraction, production change or suppression is introduced. Replacing entire setups with the larger subscribed-device helper would also alter their queue-drain sequence, so the smaller expectation-only substitution preserves more behavior.

The [completed qualification report](2026-10-29_01-47-50.md) records actual hosted macOS TSAN, ASan/UBSan and leak suites passing, all 39 technical workflow definitions succeeding, and no actionable Copilot/CodeRabbit findings. These results support the correction; they do not prove deterministic rejection of the old ordering or zero future flakiness. No controlled delayed-SubscribeResponse runtime regression was obtained, and passing per-method traces are unavailable. Darwin-owner review remains the appropriate confirmation. The recommendation is smallest reasonable existing-pattern fix, not proven uniquely smallest or guaranteed uncontroversial.
