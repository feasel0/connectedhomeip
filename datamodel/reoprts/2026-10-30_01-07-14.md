## Source Trace

`OperationalSessionSetup::CleanupCASEClient` detaches its member before scheduling `[clientPool, caseClient]`. This protects against use of the setup object after it is released, but does not keep either captured object alive. Failure to obtain a SystemLayer or schedule work explicitly leaks the client; it is not a shutdown ownership mechanism.

`DeviceControllerSystemState::Shutdown` in `src/controller/CHIPDeviceControllerFactory.cpp` shuts down the CASE manager, deletes the setup pool, and deletes the CASE client pool. The documented CONFIG_DEVICE_LAYER sequence stops the event loop before controller shutdown. The POSIX platform manager holds pending events in `mChipEventQueue`; its shutdown does not explicitly drain or cancel this queue. A stopped loop is not proof that all queued release work has completed. Restart and queue-retention behavior is platform-specific; the native probe below demonstrates dispatch after pool destruction without claiming a complete controller shutdown/reinitialization reproduction.

`OnSessionEstablishmentError` moves out of Connecting, thereby scheduling cleanup, then calls `Resolver::TryNextResult` synchronously. The resolver directly calls `OnNodeAddressResolved`; `UpdateDeviceData` calls `EstablishConnection`, which allocates before the old queued release has run. The capacity failure therefore occurs before an alternate CASE handshake. Synchronous recursive delivery can consume additional cached addresses, not merely delay one attempt.

The immediate success release is deliberate in `MoveToState`: it makes the slot available before application success callbacks can initiate another establishment. `PairingSession::Finish` clears the delegate before notifying it, and does not subsequently access members. `CASESession::OnMessageReceived` captures its metric key before `HandleStatusReport`, with an explicit warning that success may destroy `this`; after successful return the inspected branch uses local variables. `AbortPendingEstablish` likewise invokes its failure notification last after Clear. This is a fragile but visible destruction-permitted callback contract, not evidence that every pending asynchronous CASE task is safe.

## Recommended Design

Recommend a completion/cleanup owner coordinated with CASE manager and pool teardown. Track each detached client until its callback stack is safe to leave, release it exactly once, and only then continue the corresponding retry. Shutdown must invalidate or cancel continuations and finish or cancel all pending releases before destroying the pool. Retry continuations need a lifetime-safe token or explicit setup ownership, not a raw `this` or lookup-handle capture. Preserve attempt budgets, Busy delay, cancellation, callback notification count and prompt capacity reuse.

| Approach | Benefit | Material risk or obligation |
| --- | --- | --- |
| Explicit callback-completion ownership plus coordinated pending-release owner | One coherent place to define destruction, retry and shutdown ordering | Changes callback/pool ownership contracts; needs CASE and controller owner agreement and bounded embedded-memory design |
| Shutdown-aware deferred release with generation/cancellation tokens, then sequenced retry | Can fit the existing event-loop implementation | Must prove cancellation removes every stale callback, releases each client exactly once, and does not retain setups or leak during scheduler failure |
| Retain pool/system state until queued release completes | Makes the captured owner lifetime explicit | Can indefinitely retain resources when the loop stops; may create shutdown cycles or require a guaranteed drain mechanism |
| Release inline and retry synchronously | Frees capacity immediately | Reopens callback re-entrancy/destruction risk and does not resolve other outstanding background CASE work |
| Defer success and retry indiscriminately | Superficially uniform cleanup | Extends fixed-pool occupancy and can break reentrant success-callback allocation; unsafe without the same coordinated ownership design |

Precise decision: should CASE establishment callbacks formally permit immediate destruction, with explicit completion ownership for the paths that cannot, or should all completion paths transfer clients to a shutdown-aware cleanup owner? Recommend the latter only with a completion boundary that releases capacity before retry or application continuation. Authorize one coherent implementation and its contract, rather than independently changing the boolean cleanup flag, adding smart pointers, or queueing a retry.

Required regression gates for that implementation: pool-at-capacity TIMEOUT and BUSY alternatives; success callback starting another establishment; cancellation before continuation; shutdown with queued cleanup followed by restart; scheduling failure; exactly-once destruction; callback-unwind and background CASE work under sanitizers. None is claimed repaired here.
