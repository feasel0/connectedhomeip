## Findings and Recommendations

### 1. EAP: Decide the Wire Contract, Not Just the Decoder Mapping

**Priority: high compatibility decision, not a demonstrated current-development regression.**

Both Linux decoders convert their internal EAP sentinel into `kWpa3MatterPdc`, bit 0x20. The authenticated in-progress specification chapter defines that bit as generic IEEE 802.1X, covering Enterprise and per-device credentials. Older provisional contracts and existing public names describe PDC specifically. A consumer using that older meaning can interpret an ordinary enterprise network as PDC-capable. Numeric specification version 1.7 and cluster revision 3 do not distinguish these provisional revisions.

- Code: [WpaSupplicantClient.cpp](https://github.com/project-chip/connectedhomeip/blob/f5b3e64018aa7d1e1697127ebd47ce686e8e5bab/src/platform/Linux/WpaSupplicantClient.cpp#L368) and [ConnectivityManagerImpl_NetworkManagementWpaSupplicant.cpp](https://github.com/project-chip/connectedhomeip/blob/f5b3e64018aa7d1e1697127ebd47ce686e8e5bab/src/platform/Linux/ConnectivityManagerImpl_NetworkManagementWpaSupplicant.cpp#L1642).
- **Recommendation:** retain generic-EAP reporting for the current in-progress development contract, explicitly exclude automatic legacy backports, and handle stale public-name/model alignment as a separate compatibility-reviewed change. Do not silently change both decoders to PDC-only on the assumption that an older generated name establishes the intended development semantics.
- **Decision needed:** is this current-development-only, or must it work with deployed consumers that interpret bit 0x20 as PDC-only? For the latter, establish a real product/release contract first; guessing a runtime gate from 1.7/revision 3 is insufficient.
- The newly published Suite-B-192 handling and direct/TLV tests address the earlier recognition gap in both decoders. That is no longer an outstanding recommendation.
- The private chapter was read locally with provenance at specification commit `44f620f218fec98537b83f3f236834c584a0d26d`, chapter blob `7a75e1f9755def0c73c2f4201c5e8f2f8ecec6d5`; no private source text is reproduced here.

### 2. Closure Configuration: Seven Guards Encode an Additional Lifecycle Policy

**Priority: medium design decision; not redundant arithmetic checks if invalid objects intentionally remain usable.**

[Config validation and construction](https://github.com/project-chip/connectedhomeip/blob/9bebbf3c22e1396b902f14ba8148e85d1c036cc9/src/app/clusters/closure-dimension-server/ClosureDimensionCluster.cpp#L46) cache `mPositioningConfigValid`. Seven entry points test it: Startup, ReadAttribute, InvokeCommand, and four setters. Generated configuration is also validated before construction. Other invalid feature combinations already abort in this constructor, so the new code introduces a different policy for invalid Resolution/StepValue: construct a permanently unusable object and reject subsequent operations.

- **Recommendation:** prefer the existing constructor-invariant model for directly constructed objects: retain `Config::ValidatePositioning()` for graceful rejection in CodegenIntegration, enforce it in the constructor for programmer errors, and remove the cached flag and distributed guards. Keep the validation criteria and valid-configuration regression tests.
- **Decision needed before changing this:** do products require direct invalid construction to remain nonfatal? If yes, the current extra machinery buys that behavior and should not simply be deleted. Document that contract; longer term, a fallible construction/registration boundary would be cleaner than adding guards to every new mutator.
- The tradeoff is repeated branches, an instance flag, and an ongoing guard-maintenance obligation versus terminating on invalid direct construction. No measured flash/RAM delta is claimed. These are configuration guards, not redundant Interaction Model path checks.

### 3. Push AV: Enforce the Product's Zone Cap Before Allocating Duplicate-Tracking Nodes

**Priority: medium embedded-resource hardening; old Motion allocation behavior expanded to new paths.**

[ValidateMotionZones](https://github.com/project-chip/connectedhomeip/blob/14583f7600a7be821f328a8965df9e5445335e67/src/app/clusters/push-av-stream-transport-server/PushAVStreamTransportLogic.cpp#L893) computes the list size, inserts distinct IDs into a heap-backed `std::set`, and only then calls `ValidateMotionZoneListSize`. A product with a small maximum therefore allocates and processes entries that it will reject. The set already existed for Motion allocation; extraction extends this ordering to AmbientContext and modification. Input remains bounded by transport/message limits; this is not a claim of unlimited remotely controlled allocation.

- **Recommendation:** call the delegate's size check immediately after successful ComputeSize, before populating the set. Add an oversized-list regression showing that zone validation and transport allocation/modification delegates are not called. Preserve the existing status behavior for independently invalid cases.
- If a list has both excessive length and duplicates, moving the check changes which error wins. Confirm any required error precedence; if duplicate precedence is mandatory, use bounded/no-allocation duplicate detection rather than ignoring the resource limit.
- **Do not split the owning-storage correction:** AmbientContext zones need copying and list rebinding for persistence/readback. Accepting them without storing them would leave the user-facing fix incomplete. The vector/list ownership mechanism is pre-existing and is not a new general storage abstraction.

### 4. XML Generation: The Added Regression Module Is Not Registered in Normal CI

**Priority: medium verification gap, not an observed generation failure.**

[test_generate_spec_xml.py](https://github.com/project-chip/connectedhomeip/blob/f0e950f00b720b8006e28050041cc2411ef6cd6c/scripts/spec_xml/test_generate_spec_xml.py#L14) supplies a manual unittest command. At this PR head, the checked workflow/scripts contain no invocation or discovery rooted at `scripts/spec_xml`; the Python-support workflow enumerates its modules explicitly. Passing other PR checks therefore does not establish that these six regressions executed.

- **Recommendation:** add the six-test command to an existing Python-support CI step with its Matter Python dependencies, or register the module in an established discovery target. Include that small wiring change in this PR.
- The production change itself is cohesive: exact-basename filtering protects selection, while combined/legacy detection selects the appropriate include source. I found no concrete supported-layout regression warranting removal of the fallback, a new parser abstraction, or a split PR.
- Fresh local result: all six regressions passed, including combined and legacy selection, optional models, and Make failure propagation. Make/Alchemy are mocked in this suite; this is not a fresh full-spec generation run.

### 5. IDM: More Probes Are Not Automatically More Valid Constraint Coverage

**Priority: medium test-validity caveat; pre-existing behavior surfaced by the fix.**

The [numeric fallback](https://github.com/project-chip/connectedhomeip/blob/227191ff80208e1584a7acad588fa8671901b420/src/python_testing/support_modules/idm_support.py#L1498) is limited to supported numeric types with a lone nonnegative static maximum. I found no reason to broaden it or remove its negative-control tests. However, the same helper's existing octet-string filler uses zero bytes. A [human review observation](https://github.com/project-chip/connectedhomeip/pull/74959#pullrequestreview-5677996768) reports that a no-violation PayloadTestRequest already returns ConstraintError for the all-zero EnableKey. Length probes can then appear to succeed for an unrelated reason. The reviewer explicitly treated this as nonblocking and pre-existing.

- **Recommendation:** keep this PR focused on numeric sibling setup. In a separate IDM validity PR, provide command-specific valid setup where required and/or establish a valid baseline before crediting field-specific rejection, with due care for command side effects. Add a negative control proving an invalid baseline cannot count as enforcement.
- Distinguish unrelated InvalidCommand responses from genuine field-constraint enforcement, including the reported Color Control enum warnings. Do not relabel those warnings as successful coverage.
- Fresh local result: all 30 offline unit tests passed, including encoded sibling values, unsupported/unresolved setup rejection, and simulated-acceptance accounting. No fresh DUT reproduction of the EnableKey observation was attempted.

### 6. Closure SetTarget: The Existing Step Path Can Actuate Before Rejecting an Off-Grid Target

**Priority: medium existing behavior caveat; keep its correction separate.**

[Step processing](https://github.com/project-chip/connectedhomeip/blob/fd2d1454ac43b2e02526707379d0b76cd8754e6b/src/app/clusters/closure-dimension-server/ClosureDimensionCluster.cpp#L573) still clamps an increasing position to 10000 and calls `HandleStep` before `SetTargetState` validates the candidate. With a valid Resolution=3, StepValue=3, CurrentPosition=9999 and an increase of one step, it computes 10000, calls the delegate, then fails because 10000 is not divisible by 3. A failure response can therefore follow a delegate side effect. This is a static trace of the current code, not a newly executed native test.

- **Recommendation:** open a separate Step correction/decision rather than expanding the SetTarget rounding PR. Resolve the tension between maximum clamping and resolution-grid validity, test that example, and validate any rejected candidate before delegate side effects.
- Both the configuration PR and SetTarget PR leave this path otherwise unchanged. Neither should be presented as fixing all Closure Dimension positioning safety.
- The SetTarget change itself appropriately bounds rounding and reuses a validator to reject candidates before its own delegate. Valid LimitRange endpoints are required to be resolution multiples, so I did not establish the speculative limit-range regression considered during review.
