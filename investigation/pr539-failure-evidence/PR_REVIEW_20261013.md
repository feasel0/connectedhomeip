## Historical Findings

### R1: FIXED (P2) - Observing a Callback Is Not Proof That the DUT Reset Succeeded

Resolution: **FIXED** in PR550 `2b0feed`; the original counterexample follows.

Affected: PR550's target guard and the pre-existing handlers shared with PR549.

Code: [start handler](https://github.com/feasel0/matter-qa/blob/599142e5378b174f555e68a78fbb3739180d97f7/src/matter_qa/scripts/reliability_scripts/TC_RT_2_1.py#L408), [completion handler](https://github.com/feasel0/matter-qa/blob/599142e5378b174f555e68a78fbb3739180d97f7/src/matter_qa/scripts/reliability_scripts/TC_RT_2_1.py#L418), [guard](https://github.com/feasel0/matter-qa/blob/599142e5378b174f555e68a78fbb3739180d97f7/src/matter_qa/scripts/reliability_scripts/TC_RT_2_1.py#L425).

Both callbacks set commissioning_target_stage_seen before factory_reset_dut. ctypes reports but does not propagate a Python callback exception to the waiting coroutine. A control using the actual callback type raises on the target reset, then permits subsequent operations; factory_rest_during_commissioning returns normally with the flag true.

This is an inherited harness defect, not a demonstrated regression introduced by PR550 and not an observed new physical failure. The new guard fixes missing notification but does not establish successful fault injection. Failing DUT adapters can therefore be mistaken for valid reset-stage coverage.

Minimal direction: record callback reset success/error in ordinary Python state and check it before accepting expected commissioning failure or proceeding. Preserve the primary reset exception. Do not broaden stage selection, add retries or alter SDK behavior.
