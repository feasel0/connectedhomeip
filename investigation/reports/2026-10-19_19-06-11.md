## Accepted Upstream Correction

- Discussion: https://github.com/bluez/bluez/issues/1094
- Reporter-confirmed test: https://github.com/BluezTestBot/bluetooth-next/pull/2720
- Mainline correction:
  https://github.com/torvalds/linux/commit/b25120e1d5f2ebb3db00af557709041f47f7f3d0
- Stable 6.12.18 changelog:
  https://cdn.kernel.org/pub/linux/kernel/v6.x/ChangeLog-6.12.18

The patch, `Bluetooth: L2CAP: Fix L2CAP_ECRED_CONN_RSP response`, was authored
February 14, 2025 and committed February 20. It fixes
`9aa9d9473f1550d1936c31259720b3f1f4690576`. Stable backport
`5c9921f1da47c0b4f12e836ef8778f024a241ada` is included in 6.12.18, released
March 7. The first mainline release was not independently established here.

The final accepted correction has two components:

1. `__l2cap_chan_add` uses `list_add_tail(&chan->list, &conn->chan_l)` so the
   responder's deferred response preserves incoming channel order.
2. `l2cap_ecred_rsp_defer` skips outgoing channels and channels not marked for
   deferred setup, using `FLAG_ECRED_CONN_REQ_SENT` and
   `!test_and_clear_bit(FLAG_DEFER_SETUP, &chan->flags)`.

The intermediate `BT_CONNECT2` state filter is not the accepted correction:
channels were already connected when the response was assembled, producing
empty responses. The final flag filter also excludes established channels
whose identifier happens to match a later request. The issue's initial Pixel
multi-channel symptom and the later Redmi single-channel extra-DCID symptom
explain why both components matter. The reporter confirmed the final test
fixed the issue. TestBot L2CAP/build checks passed, but management results had
four privacy failures and four not-run cases; not all CI passed.

## Distinct Requester Candidate and Native Check

The matching source's `l2cap_ecred_connect` writes the triggering channel into
request position zero, then `l2cap_ecred_defer_connect` appends deferred
siblings in connection-list order, assigning the same identifier. However,
`l2cap_ecred_conn_rsp` consumes DCIDs by connection-list order, not transmitted
SCID order. `__l2cap_chan_add` appends and `l2cap_alloc_cid` chooses the first
free CID, supporting an initial list `[64,65]` with triggering65 and request
`[65,64]`. The original in-memory list and eligibility state were not retained.

For that list, a correct response `[64,65]` is assigned internally as
DUT64 -> controller64 and DUT65 -> controller65, instead of the advertised
DUT65 -> controller64 and DUT64 -> controller65. A normal same-socket ATT reply
to a request received on DUT64 then arrives at controller64, exactly the
observed mismatch. BlueZ need not select another socket for this to occur.

New `investigation/tools/ecred_order_probe.py` fetches or reads only the
hash-matching source, extracts the complete grouping/request functions and
response handler unchanged, and compiles them with `cc -std=gnu11 -Wall
-Wextra -Werror`. Bounded host stubs supply list traversal, flags, channel state,
send recording and no-op transport/security callbacks. The probe does not load
a module, run BlueZ, send traffic or modify either peer. Success-only control
paths are exercised; teardown/security stubs abort if unexpectedly reached.

| Isolated case | Actual request | Actual assigned local:peer | Positional mismatch |
| --- | --- | --- | --- |
| One channel, trigger64 | `[64]` | `64:64` | no |
| Two channels, trigger64 | `[64,65]` | `64:64,65:65` | no |
| Two channels, trigger65 | `[65,64]` | `64:64,65:65` | yes |
| Three channels, trigger66 | `[66,64,65]` | `64:64,65:65,66:66` | yes |

The two-channel mismatch matches all six historical negotiation lists. A
changed-source negative control is rejected. Eight further negative checks
reject bad request/response role, identifier, result, PSM, request CID,
response CID and frame order, with an identical-input positive control.

The first native attempt aborted because the test shim modeled the response
with a fixed CID array, changing `sizeof` from the kernel flexible-array
header. Correcting only that shim produced the results above. This was a
diagnostic defect, not a reproduced DUT failure. A later event-count check
initially used the wrong capitalization; the corrected case-insensitive check
passed against the same originals without changing their content.

No accepted correction for this requester-side candidate was identified.
Inspected modern mainline retains the triggering-first request and list-order
response consumption; a generic kernel upgrade is not a demonstrated fix.
No candidate production change is justified solely by the host probe.
