not only through an ATT response arriving on the other advertised bearer.
This is evidence for case B under the verified deployed kernel handler.

### Why This Exposes Stored State

The exact package-named Raspberry Pi source is still pinned to
`359f37f0faefb712add32a39f98751aea67d5c1f`, L2CAP source SHA256
`40b71702ffee7a0e47d3f3c12861d3fc1cb235a67fa3e1bd3407fd56a860aaa8`.
Its unchanged `l2cap_disconnect_req` does the following:

1. Looks up the channel by local SCID equal to the request DCID.
2. Sets response DCID from `chan->scid`.
3. Sets response SCID from `chan->dcid`, not from the request SCID.
4. Sends that response before deleting the channel.

Consequently, response `(65,65)` exposes DUT local65 -> controller65, contrary
to the advertised local65 -> controller64 association. No ATT socket-selection
decision is involved in constructing this kernel signaling response. Merely
echoing the controller's request would have produced `(65,64)`, not the bytes
retained in all six originals.

a02 and a03 also contain DUT-originated Disconnection Requests `(DCID64,
SCID64)` at frames171 and107. The controller answers `(DCID64, SCID65)` at
frames173 and109. These support disagreement about the other pair as well;
the primary six-attempt conclusion does not require those two extra exchanges.
