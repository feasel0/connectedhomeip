## Assessment

1. The coroutine observation is plausible as a harness-defect lead, but is
   not established as the cause of the CASE Busy issue. The inspected
   attachments contain Busy failures without the reported warnings.
2. Dual discovery is intentional SDK behavior. BLE and DNS-SD must not be
   treated as interchangeable, but seeing both in a ble-thread run is not
   itself evidence that the testers mixed them up.
3. QR versus manual setup code is a useful controlled discriminator-width
   experiment, not a binary root-cause verdict. We already have a specific
   independent wrong-peer case with stronger evidence than a rate comparison.

The [2026-07-09 retest comment](https://github.com/project-chip/connectedhomeip/issues/33830#issuecomment-4923633765)

A never-awaited coroutine means that invocation's body did not run. If it
was cleanup, session invalidation, or reset sequencing, omission could leave
state behind or permit overlapping work. That is a real defect to investigate,
but it does not automatically explain why a remote CASE responder was Busy.
Warnings can be emitted when coroutine objects are finalized, not exactly
when the missing await occurred. Temporal proximity alone is insufficient.

The deciding next evidence would be the exact coroutine name and allocation
site, originating run and iteration, executed QA/SDK revisions, and matched
CASE exchanges identifying the handshake that owned the responder when Busy
was returned. These were not supplied with Cecile's quotation. The negative
search above is limited to the named attachments, not every log in existence.

### SDK and Independent Evidence

In the inspected SDK checkout at
`2a13c27540d1d1d12a078a6a3c16a11be1ae94a2`,
`src/protocols/secure_channel/CASEServer.cpp:85` tests whether the responder
already has a handshake in progress. If the watchdog does not reclaim it,
the server sends Busy and preserves that handshake. Busy can therefore be
legitimate contention; it does not alone establish a stuck session or an SDK
defect. Conversely, a stuck owner or defective recovery could still be an SDK
bug, and the issue should not be dismissed solely because Busy is supported.

The previously sealed independent serialized RT_1_2 analysis identifies
simultaneous background resubscription CASE attempts on several fabrics:
TH-2 owns one handshake and TH-3/TH-4 receive Busy. Serial foreground reads
did not serialize background recovery. See
[the 2026-10-17 report](2026-10-17_18-26-24.md), section TH-3 CASE Busy.
That demonstrates an alternative mechanism in that experiment, not the root
cause of the original 2024 issue or the July retest.

## What the Two Discovery Paths Mean

Source inspection, not a new runtime test, establishes the following:

- `src/controller/python/matter/ChipDeviceCtrl.py:3619` defaults
  CommissionWithCode to DISCOVERY_ALL.
- `src/controller/SetUpCodePairer.cpp:102` starts eligible rendezvous methods,
  including BLE, then also starts DNS-SD discovery. The source explicitly
  explains that already-networked devices may be commissioned on-network
  regardless of the QR rendezvous flag.
- `src/controller/SetUpCodePairer.cpp:247` selects short or long DNS-SD
  filtering from the parsed setup payload.
- `src/controller/SetUpCodePairer.cpp:565` places an available BLE candidate
  at the front of the pending candidates, supporting fallback between paths.

There are two distinct appearances of DNS-SD in this workflow: initial
commissionable discovery/PASE can compete with BLE discovery/PASE, and later
operational discovery locates the commissioned node for CASE over IP. A
ble-thread label describes a provisioning workflow; it does not prove every
discovery or session in the run used BLE. CASE itself is not a BLE session.

Issue 72252 expressly reports the first situation: a UDP PASE attempt times
out and the controller falls back to BLE with invalid GATT state. A stale
DNS-SD candidate may trigger that sequence, but it does not excuse a NULL C1
crash. SDK transport ownership and callback cleanup must remain robust when
discovery returns multiple candidates or one transport fails.

## QR-Code Experiment

The inspected manual-payload parser creates a short discriminator. A manual
setup code conveys four discriminator bits; a QR payload can convey the full
12-bit discriminator. Each short bucket therefore contains 256 long values.
The full discriminator is a narrower discovery filter, not a unique device
identity or an authentication guarantee.

The sealed October 17 fixture incident already demonstrates a collision:
Nordic discriminator 3840 and a separate Pi enhanced-window discriminator
4021 both map to short discriminator 15. The controller selected the Pi over
IP and attempted PASE, with controller/DUT exchanges matched in the retained
evidence. Its pinned runtime generated a manual code when setup_code was
absent. See [the original attribution](2026-10-17_18-26-24.md), section
Iteration 75: Wrong-Peer PASE. This proves that incident's wrong-peer path,
not that all instances of 36974, 38750, or 72252 share it.

A discriminating comparison should keep the same code revision, hardware,
credentials for the active commissioning window, reset/readiness handling,
logging, and competing advertisers. Change only manual versus full-width
payload filtering where practical. Match rendezvous information deliberately
and verify the actual parsed payload/filter and selected peer in native logs;
do not assume supplying a QR string prevents a helper from generating another
manual code. An enhanced window needs its current payload, not a stale
factory QR code. Do not overlap or perturb protected campaigns.

Interpret outcomes by failure phase, not only overall iteration failure rate:

- Fewer confirmed wrong-peer/PASE failures supports the collision hypothesis.
- An unchanged aggregate failure rate does not exclude a collision if other
  failures dominate, the sample is too small, or the intended long filter was
  never applied.
- Continued failure to the verified correct peer under the long filter weakens
  that explanation for those failures and redirects attention to readiness,
  GATT lifetime, transport loss, or later operational discovery/CASE.
- QR does not disable DNS-SD, repair later CASE contention, or prevent every
  collision with another device using the same long discriminator.

No physical A/B test or new failure-rate estimate was produced in this turn.
