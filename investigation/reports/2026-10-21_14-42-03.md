## Ordered Investigation Plan

### 1. Establish Provenance and Finish CASE Attribution

First obtain the actual newest CI failure, its SDK/QA commits, controller
wheel or native-library hash, DUT firmware identity, relevant build flags,
and a neighboring confirmed PASS. Preserve the latest failure privately.
Keep reporter statements, repository refs, and executed binary identity as
separate evidence fields. Do not block analysis of July logs while waiting.

For Busy failures, align controller and DUT native exchange IDs/counters to
identify the handshake occupying the responder, its start, completion or
timeout, and other foreground/background clients. Record Busy wait values,
retry scheduling, attempt budgets, resolver retries, and callback outcome.
Treat iterations 10/19 as timeout controls, not extra Busy examples.

In parallel within this same evidence task, locate Cecile's exact warning and
resolve its coroutine creation site. Audit only the implicated cleanup,
unpair, reset, cancellation, or teardown path at the executed QA revision.
Compare the same warning in actual passing iterations. A cleanup omission
must be shown to precede and explain persistent state before attributing Busy
to it; garbage-collection warning timestamps alone are not causal evidence.

Decision gate: classify legitimate concurrent-handshake contention, stuck
responder ownership, controller recovery/budget failure, harness lifecycle
omission, or insufficient evidence. Require a focused reproducing regression
before a production repair. Do not increase retry/timeouts speculatively.

### 2. Validate Existing Fixes on Exact Builds

Use the current upstream baseline and the existing targeted fixes on a
matched base, recording actual revisions and compile-time configuration.
Start with focused native regressions: exhausted-budget Busy recovery and
bounded repeated Busy for 33830; overlapping UDP PASE/BLE completion,
disconnection before fallback, cancellation, and fresh reconnection for 72252.
Reuse existing tests. No new multi-fix branch or broad redesign is needed.

For a justified later fixture diagnostic, distinguish commissionable discovery
transport from the PASE transport actually attempted. Compare single and
concurrent commissionable discovery only where supported, keeping normal
operational DNS-SD/CASE available. Readiness, DUT boot advertising, and window
state must be verified first. Success requires clean ownership/callback
completion as well as no crash; fewer crashes alone do not establish the
lifetime invariant. SDK memory corruption in 42947 remains a separate path.

### 3. Gate the QR Experiment on the Real Runtime Path

For 36974/38750 and related commissioning failures, first identify whether
the correct DUT was advertising with an eligible commissioning window and
which setup payload/filter the executed helper actually used. A QR change
does not replace reset-readiness validation or operational discovery checks.

Use the following minimal comparison only when that evidence warrants it:

| Arm | Controlled change | Purpose |
| --- | --- | --- |
| A | Current QA invocation, traced through its actual helper | Establish the real baseline, not an assumed long-filter baseline |
| B | Current-window QR payload with matching rendezvous configuration | Compare long-filter peer selection against A |
| C, conditional | Explicit manual-code arm only if A is genuinely different | Separate code-path changes from short-filter matching; omit if A already generates that manual code |
| D, conditional | Restrict initial discovery transport where supported | Test transport competition independently of discriminator width; do not disable later operational DNS-SD |

Keep firmware/controller builds, reset gates, credentials, logging, and
competing advertisers fixed. Record selected peer and filter width per
attempt. Use the current enhanced-window payload where applicable, not an
old factory QR. Keep commissioning domains isolated from other campaigns.

Specify the sampling budget and smallest useful effect before a rate test,
using measured baseline frequency; an arbitrary ten-run sample is not proof
for a rare issue. Report per-phase counts and requested/executed/pass/fail/
incomplete denominators. A reduction in verified wrong-peer PASE supports
the collision explanation; unchanged aggregate failures do not exclude it.
QR cannot guarantee uniqueness or explain an operational CASE/double-free
failure by itself.

### 4. Close Each Mechanism Separately

The output should be one evidence matrix with executed revision, actual
discovery/PASE path, failure phase, warning provenance, responder owner,
and disposition per failure. A harness bug belongs in a scoped QA fix; an SDK
bug needs a failing native regression and matched positive control. Keep
42947 timeout and double-free attribution separate. Do not use one rare
failure's disappearance to declare all listed issues resolved.

Hardware work above is a proposed next stage, not a launched or implicitly
approved campaign. Recheck current fixture ownership, required lab procedures,
and the user's hardware scope before execution. The immediate completed work
is attachment triage and this merged plan.
