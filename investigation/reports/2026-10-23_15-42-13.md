## CASE: Remaining Evidence and QA Request

Rechecked the entire existing July ZIP, SHA256
`db929fad98798f3cb670ddee18ab4d4368a6f9ac35161fe3f08722d177a7eab0`:
28 files, comprising seven controller application logs, seven iteration JSON
records, seven controller Bluetooth service logs and seven controller Wi-Fi
service logs. No dedicated DUT log or executable-build manifest is present.
The seven JSON records have iteration_data/iteration_number roots; recursive
inspection found no commit, firmware, SDK-version or binary/wheel-hash fields.
Whitelisted scanning of all21 text logs found no responder-handshake ownership
markers. Controller service logs cannot identify the DUT's active CASE object.

The published request-exchange/Busy5000ms references remain the strongest July
evidence; counts remain four Busy FAILs, two timeout FAILs and one PASS.
The May late Sigma2Resume matched the retired exchange with a null delegate
and received an ACK. Neither observation identifies which responder handshake
was active when another request was rejected. Busy5000ms is not an owner ID
or proof of a stuck handshake. In the inspected CASEServer implementation,
5000ms can be a fallback delay; even a computed Sigma2 wait is not a lifecycle
trace. The Busy branch need not print its retained owner at all.

QA must supply one correlated failing iteration, not a new large campaign:

1. Continuous DUT native CASE/secure-channel, exchange-manager and session logs
   from boot/reset or the preceding accepted Sigma1 through the first Busy,
   the configured handshake deadline, and completion/timeout/abort/release.
   Include boot identity, UTC/monotonic timestamps and controller/DUT clock
   alignment. A log beginning after Busy can omit the actual owner.
2. Distinguish the incoming rejected exchange from the retained CASE exchange:
   exchange IDs/roles, process-local context IDs where logged, CASE state and
   transitions, session IDs, transport/source/destination endpoints, and scoped
   peer/fabric identity where known. Record actual timer expiry/cancellation,
   watchdog outcome and release, not just a nominal timeout value. If existing
   logging omits the retained owner, state that explicitly and supply an
   already-available read-only diagnostic snapshot if possible; more controller
   Busy lines alone do not fill that gap.
3. DUT SDK/platform/vendor-firmware commits and local diff, board/application,
   exact flashed-image SHA256, matching ELF/build ID and symbols, build arguments
   and consumed configuration: CASE resumption/retries, MRP timing, watchdog
   settings and any active fault injection. A branch name is not binary proof.
4. Controller QA and SDK commits/diffs, launch command and commissioning options,
   actual loaded Python package/native-library paths and hashes, wheel or other
   executable identity, relevant retry/resumption settings and MRP values.
   Pair these with the existing controller trace for the same iteration.

Preserve failure/reset boundaries and peer mappings when redacting. Do not
request or publish session keys, resumption secrets, passcodes or credentials.
Until supplied, transient contention and a retained/stuck responder remain
unresolved alternatives. Missing-await causality is not established either.

## Discriminator: One Worthwhile Bounded Correction

Fresh read-only pins: QA main `62fd652d30a77b72bf3bc10b007db9c1073b8458`;
upstream SDK master `4e7d39789484887a048371b3214e87a9a68a1fc0`.
The QA adapter's pair_device AST is unchanged from tested QA `52f3a168`.
Current SDK get_setup_payload_info_config still assigns LONG_DISCRIMINATOR
and setup_code=None for raw numeric input; Commission's PASE helper still
calls CreateManualCode. The CLI declares LONG_DISCRIMINATOR, so this implicit
conversion contradicts that path's declared precision. Legitimate supplied
manual codes are not defective and must remain short.

Proposal only: in Commission._find_or_establish_pase_if_needed, for absent
setup_code plus LONG metadata, generate a full-width QR with the existing
SetupPayload.GenerateQrCode API, then retain FindOrEstablishPASESession and
its current Thread MeshCoP arguments. Leave supplied QR/manual strings and
short-discriminator behavior unchanged. Do not switch the helper wholesale
to CommissionOnNetwork or alter the separate, already-long additional-fabric
QA call site.

The implementation must explicitly preserve discovery eligibility: manual
payloads omit rendezvous information and ShouldDiscoverUsing returns true for
every channel. GenerateQrCode defaults to on-network capability4, which would
not preserve that behavior. Use the existing recognized channel flags for
this synthetic payload (the inspected six-flag set is0x3f), not the default;
do not invent a discovery mechanism. Explicit vendorId=0/productId=0 avoids
inventing the generator's default test-product identity and is allowed by
the existing payload validator. Keep normal discriminator/passcode validation.

The intended regression is clear: extend existing commissioning unit coverage
and TestSetupPayload, without a new framework. Raw LONG3840 must reach PASE as
a QR that matches3840 but excludes4021, and conversely; supplied manual must
still accept their shared short15 bucket; supplied QR/manual bytes and raw
SHORT behavior must stay unchanged. Check recognized discovery channels,
unspecified VID/PID, invalid-input error propagation, and unchanged MeshCoP
host/port forwarding. The existing published offline harness can check the
helper boundary; native payload tests check encoding/filter semantics. These
are proposed acceptance tests, not newly executed results.
