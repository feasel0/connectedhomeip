### DUT Progress

Status callbacks transition their exact handlers to state 1 and execute report
confirmation. ScheduleRun is entered within approximately 0.035-0.063 ms and
Engine::Run within 0.051-0.093 ms of status dispatch. Twelve engine runs occur
before each corresponding handler's next visit; their entry in-flight counts
are 3. Thus scheduling itself is prompt and the engine continues running;
neither a permanently lost confirmation nor a several-second failure to
schedule Engine::Run explains these observations.

The next actual visits occur after approximately 7.263-10.227 seconds, become
eligible immediately, and enter the builder immediately. Builder entry to
message preparation is only approximately 2.9-7.0 ms. Prepared messages have
successful socket-send records and byte-identical captured payload counterparts
on both endpoints. The long interval is chiefly before handler revisit, not
inside report construction. Shared report capacity, progress of other handlers
and controller consumption remain competing explanations; these counters do
not by themselves prove an incorrect fairness algorithm.

### Ubuntu Delivery

For all six exchanges, the exact next-report payload reaches the Ubuntu
infrastructure capture before timeout; corresponding recvmsg and authenticated
dispatch records occur afterward. The first demonstrated delayed controller
boundary is therefore capture ingress to socket receipt, not a native RX log
timestamp, decryption, or a missing network packet. Host UTC/monotonic offset
changes by only -320 ns between the paired anchors; this local comparison
does not rely on calibrating the Pi clock against Ubuntu.

Three earlier capture-to-socket windows overlap about 2.503, 1.656 and 0.764
seconds of ProcessReportData on the same native thread. Other windows do not;
this overlap is evidence of shared-thread work, not a complete causal stack.
The longest measured controller ProcessReportData span is about 1.424 seconds.
The longest synchronous controller logging call is 84.123 ms, not a
multi-second single logging block. Aggregate logging cost and uninstrumented
Python callback work are not excluded. Sixty KeyError renderings and an early
TypeError also exist, but no causal attribution is made from their presence.

The remaining discriminating work is a bounded offline correlation of the
retained event-loop work/callback spans and competing-handler progress, not an
automatic new invocation, increased timeout, reduced logging, serialized test,
or speculative scheduler fix. Additional live work requires a new scoped
authorization and resolution of the counters-path isolation defect.
